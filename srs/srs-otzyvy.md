## 1. Введение {#1-introduction}

Документ описывает требования к Desktop-приложению «TourReview» — системе отзывов и рейтингов для туристических мест и объектов аренды. SRS предназначен для команды разработки (JavaFX + Gradle), QA и преподавателя-заказчика. Документ определяет **ЧТО** делает система, а не **КАК** это реализовано.

### 1.1 Назначение документа {#11-document-purpose}

SRS фиксирует назначение, функциональные и нефункциональные требования к TourReview, чтобы на их основе можно было проектировать, реализовывать и верифицировать ПО. Основные аудитории: разработчики, тестировщики, заказчик (напарник) и преподаватель. Документ используется на протяжении всего ЖЦ: от планирования до приёмки.

### 1.2 Область применения продукта {#12-product-scope}

**Продукт:** TourReview, Desktop-приложение на Java (JavaFX), сборка Gradle.  
**Назначение:** пользователи оставляют отзывы, фото и рейтинги туристических мест и арендных объектов; модераторы проверяют жалобы и скрывают недопустимый контент.  
**Входит в область:** отзывы, фото, рейтинги, ответы на отзывы, жалобы, модерация, аудит действий модератора.  
**НЕ входит:** онлайн-бронирование и оплата, мобильные клиенты, интеграция с картами (в текущей версии).

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

TourReview — самостоятельное Desktop-приложение (новый продукт). Работает локально, данные хранятся во встроенной БД SQLite/H2. В перспективе возможна синхронизация с REST-сервисом (в текущей версии не реализуется). Владелец — учебный проект БГУИР; SLA не задан.

### 2.2 Функции продукта {#22-product-functions}

1. **Отзывы** — создание, редактирование, удаление своих отзывов.
2. **Фото** — прикрепление изображений к отзыву.
3. **Рейтинги** — оценка 1–5, средний рейтинг и число отзывов в карточке места.
4. **Ответы на отзывы** — арендодатель отвечает на отзыв об объекте.
5. **Жалобы** — пользователь жалуется на отзыв/фото.
6. **Модерация** — очередь жалоб, скрытие контента, аудит-лог действий.
7. **Роли и доступ** — турист, арендодатель, модератор, администратор.

**Три дополнительных требования (получены от Заказчика — напарник):**
- **BR-1:** Турист видит средний рейтинг и число отзывов в карточке места.
- **BR-2:** Арендодатель может ответить на отзыв, ответ виден под отзывом.
- **BR-3:** Модератор получает очередь жалоб и может скрыть контент; действие логируется.

### 2.3 Ограничения продукта {#23-product-constraints}

- **Должен** быть Desktop-приложением на Java + JavaFX.
- **Должен** собираться через Gradle.
- **Должен** использовать встроенную БД (SQLite/H2) без отдельного сервера.
- **Должен** работать на Windows/Linux/macOS с Java 17+.
- **Не должен** требовать постоянного подключения к интернету.

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Роль | Подготовка | Доступ | Цель |
|---|---|---|---|
| Турист | базовая | свои отзывы, жалобы | найти место, оставить отзыв |
| Арендодатель | базовая | отзывы об объектах | ответить на отзыв |
| Модератор | средняя | очередь жалоб | скрыть недопустимый контент |
| Администратор | высокая | все данные | управление пользователями |

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

- Пользователь имеет локальную Java 17+ и права на запись файла БД.
- Фото хранятся в локальной папке `photos/`.
- Внешние сервисы (карты, оплата) не используются.
- При недоступности БД приложение показывает ошибку и не теряет введённые данные.

## 3. Требования {#3-requirements}

Формат ID: `REQ-[AREA]-[NNN]`. Ключевые слова: «должен» — обязательно, «следует» — рекомендуется, «может» — опционально.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

- **REQ-INT-001** — Система **должна** предоставлять экраны: карточка места, форма отзыва, очередь модерации (мокап: [mockups.png](images/mockups.png)).
- **REQ-INT-002** — Система **должна** валидировать ввод: оценка 1–5, текст отзыва не пустой, фото — допустимый формат (png/jpg).
- **REQ-INT-003** — Система **должна** показывать сообщения об ошибках на русском языке.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

- **REQ-HW-001** — Система **должна** работать на ПК с ОЗУ ≥ 4 ГБ и разрешением ≥ 1280×720.
- **REQ-HW-002** — Система **должна** поддерживать клавиатуру и мышь; сенсорный ввод — опционально.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

- **REQ-SW-001** — Система **должна** использовать встроенную БД SQLite/H2; файл БД — в папке приложения.
- **REQ-SW-002** — Система **должна** хранить фото в локальной папке `photos/` и ссылку на файл — в БД.
- **REQ-SW-003** — Система **должна** быть совместима с Java 17+ и JavaFX.
- **REQ-SW-004** — REST-синхронизация **может** быть добавлена в будущих версиях (не входит в текущую).

### 3.2 Функциональные требования {#32-functional}

- **REQ-FUNC-001** — Система **должна** позволять туристу создать отзыв: оценка 1–5, текст, опциональное фото.  
  *Acceptance:* отзыв сохранён, отображается в карточке, средний рейтинг пересчитан.  
  *Verification:* Test.
- **REQ-FUNC-002** — Система **должна** показывать средний рейтинг и число отзывов в карточке места (**BR-1**).  
  *Acceptance:* значения совпадают с данными БД. *Verification:* Test.
- **REQ-FUNC-003** — Система **должна** позволять арендодателю ответить на отзыв; ответ виден под отзывом (**BR-2**).  
  *Acceptance:* ответ сохранён и отображается. *Verification:* Test.
- **REQ-FUNC-004** — Система **должна** позволять пользователю подать жалобу на отзыв/фото с указанием причины.  
  *Acceptance:* жалоба попала в очередь модерации. *Verification:* Test.
- **REQ-FUNC-005** — Система **должна** предоставлять модератору очередь жалоб с возможностью скрыть контент (**BR-3**).  
  *Acceptance:* скрытый контент не виден туристам. *Verification:* Test.
- **REQ-FUNC-006** — Система **должна** логировать действия модератора: кто, когда, что скрыл (**BR-3**).  
  *Acceptance:* запись в аудит-логе создана. *Verification:* Test.
- **REQ-FUNC-007** — Система **должна** разграничивать роли: турист, арендодатель, модератор, администратор.  
  *Acceptance:* недоступные действия блокируются. *Verification:* Test.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

- **REQ-PERF-001** — Открытие карточки места **должно** занимать ≤ 2 с при 10 000 отзывов.
- **REQ-PERF-002** — Сохранение отзыва **должно** занимать ≤ 1 с.
- **REQ-PERF-003** — Приложение **должно** потреблять ≤ 512 МБ ОЗУ в покое.

#### 3.3.2 Безопасность {#332-security}

- **REQ-SEC-001** — Пароли **должны** храниться в виде хэша (не в открытом виде).
- **REQ-SEC-002** — Действия модерации **должны** быть неизменяемо залогированы (аудит).
- **REQ-SEC-003** — Система **должна** проверять права перед скрытием контента.

#### 3.3.3 Надёжность {#333-reliability}

- **REQ-REL-001** — При сбое записи в БД система **должна** показать ошибку и не потерять введённые данные.
- **REQ-REL-002** — Повторное сохранение отзыва **должно** быть идемпотентным (без дублей).

#### 3.3.4 Доступность {#334-availability}

- **REQ-AVAIL-001** — Приложение **должно** запускаться без интернета.
- **REQ-AVAIL-002** — Время восстановления после сбоя **должно** быть ≤ 1 мин (перезапуск).

#### 3.3.5 Наблюдаемость {#335-observability}

- **REQ-OBS-001** — Система **должна** вести лог ошибок с меткой времени и уровнем.
- **REQ-OBS-002** — Аудит-лог модерации **должен** быть доступен администратору.

### 3.4 Соответствие стандартам {#34-compliance}

- **REQ-COMP-001** — Документация **должна** соответствовать шаблону SRS из репозитория ЛР2.
- **REQ-COMP-002** — Персональные данные **должны** обрабатываться согласно локальным политикам учебного проекта.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

- **REQ-INST-001** — Система **должна** устанавливаться из дистрибутива Gradle (`installDist`) и запускаться одним скриптом.

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

- **REQ-BUILD-001** — Сборка **должна** выполняться командой `./gradlew build` без ошибок.
- **REQ-BUILD-002** — Сборка **должна** быть воспроизводимой (фиксированные версии зависимостей).
- **REQ-BUILD-003** — Артефакты **должны** версионироваться (semver).

#### 3.5.3 Распределение {#353-distribution}

- **REQ-DIST-001** — Дистрибутив **должен** включать JRE-совместимый запуск (или требование Java 17+ в README).

#### 3.5.4 Сопровождаемость {#354-maintainability}

- **REQ-MAINT-001** — Код **должен** быть модульным (UI / сервисы / репозиторий).
- **REQ-MAINT-002** — Публичные API **должны** быть документированы.

#### 3.5.5 Повторное использование {#355-reusability}

- **REQ-REUSE-001** — Сервисы отзывов/модерации **должны** быть отделены от UI для повторного использования.

#### 3.5.6 Переносимость {#356-portability}

- **REQ-PORT-001** — Система **должна** работать на Windows/Linux/macOS с Java 17+.

#### 3.5.7 Стоимость {#357-cost}

- **REQ-COST-001** — Проект **должен** использовать только бесплатные/open-source библиотеки.

#### 3.5.8 Сроки {#358-deadline}

- **REQ-DEAD-001** — Документация SRS **должна** быть готова к концу текущей пары (согласно заданию).

#### 3.5.9 Доказательство концепции {#359-proof-of-concept}

- **REQ-POC-001** — PoC **должен** подтвердить работу JavaFX + встроенной БД на одном экране.

#### 3.5.10 Управление изменениями {#3510-change-management}

- **REQ-CM-001** — Изменения **должны** вноситься через ветку и pull-request.
- **REQ-CM-002** — Замечания бизнес-сообщества **должны** анализироваться; отклонённые — обосновываться.

### 3.6 ИИ/МО {#36-aiml}

Не применимо: в текущей версии TourReview не использует ML/AI. Раздел оставлен для будущих версий (например, авто-детекция спама в отзывах).
